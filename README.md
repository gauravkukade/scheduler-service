Scheduler owns and writes: status (only up through CREATED → DISPATCHING → READY / PROCESSOR_UNAVAILABLE / RETRY_SCHEDULED / SKIPPED_CONCURRENT / MAX_RETRIES_EXCEEDED / SKIPPED_CONCURRENT), retryCount, nextRetryAt, lastAttemptAt, everything set at creation time (jobName, jobGroup, businessDate, triggerType, etc.).
Processor owns and writes, from the point it accepts a dispatch: transitioning status from READY → PROCESSING → SUCCESS/FAILED/TIMED_OUT, failureReason, failureCategory, plus whatever richer execution detail it wants to add later (record counts, file paths, log references) — fields Scheduler's domain class doesn't even need to know about.
Both services independently maintain their own JobInstance class — same collection, same instanceId/_id, but each service's Java class only needs to declare the fields it actually touches. Processor's version can simply omit retryCount/nextRetryAt if it never reads or writes them — Spring Data Mongo doesn't require a class to map every field in a document, it just ignores what isn't declared. That keeps each side's code honest about what it actually owns, rather than pretending to a shared full schema it doesn't fully control.
